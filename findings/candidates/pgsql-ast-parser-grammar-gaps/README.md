# pgsql-ast-parser: valid PostgreSQL rejected by four grammar rules

- **Package**: [pgsql-ast-parser](https://github.com/oguimbal/pgsql-ast-parser) 12.0.2, the latest release
  (npm, about 1.3M downloads/week)
- **Class**: parse failure on valid input (a plain `Syntax error`, unlike the existing
  `findings/pgsql-ast-parser-ambiguous-syntax`, which is nearley returning more than one parse)
- **Status**: candidate, not reported. Groups A to C: no issue found on 2026-10-01. Group D and the three "known"
  rows have open issues or PRs, linked below.
- **Fixed in latest**: no. None of the open PRs (#146, #172, #174) touches rules A to C.
- **Reproduce**: `npm install && node poc.js`

This directory collects the rejections from the `sql_js` probe that are grammar gaps rather than lexer bugs. The two
lexer bugs from the same probe have their own directories: `pgsql-ast-parser-escape-string-crash` and
`pgsql-ast-parser-exponent-literal`. The project README asks for these reports ("Open an issue if you find an bug or
unsupported syntax") and does not list any of these constructs as unsupported; its only stated gap is PL/pgSQL.

Reference throughout: libpg-query 18.1.5 and pglast 8.4 (both PostgreSQL's own grammar) accept every statement below;
sql-parser-cst 0.42.1 and sql-formatter 15.8.2 accept the ones from the original probe.

## A. HAVING without GROUP BY (new)

```
SELECT count(*) FROM t HAVING count(*) > 1     Syntax error at line 1 col 24
SELECT HAVING TRUE                             Syntax error at line 1 col 8
```

`src/syntax/select.ne:13` nests HAVING inside the GROUP BY option:

```
select_statement -> select_what select_from:? select_where:? (select_groupby select_having:?):? ...
```

so HAVING can only follow GROUP BY. PostgreSQL 18, SELECT reference page, "HAVING Clause": "The presence of HAVING
turns a query into a grouped query even if there is no GROUP BY clause." The first statement is an ordinary way to
ask "does this table have more than one row", so this is the most user-visible gap here.

Fix: make the two clauses independent, `select_groupby:? select_having:?`, and adjust the postprocessor at
`select.ne:15-18`, which reads both from one tuple.

## B. Subscript followed by `::` or `->` (new)

```
SELECT a[1]::real      Syntax error at line 1 col 12
SELECT a[1]->'x'       Syntax error at line 1 col 12
```

`(a[1])::real` parses. In `src/syntax/expr.ne:101-128` the precedence levels run
`expr_array_index -> expr_member`, and both the cast and the member rule take `(expr_member | expr_paren)` as their
left operand, so the result of a subscript can never be cast or dereferenced. PostgreSQL 18 section 4.1.6, Table 4.2:
`::` and `[ ]` share the top precedence level and are left-associative, so `a[1]::real` is `(a[1])::real`.

Fix: fold the subscript, member and cast alternatives into one left-recursive postfix level, so each can take any of
the others as its operand.

## C. `->` / `->>` with a non-literal right operand (new, arguably a design limit)

```
SELECT a -> b                  Syntax error at line 1 col 13
SELECT a ->> ('k' || 'x')      Syntax error at line 1 col 14
```

`src/syntax/expr.ne:110`: `(expr_member | expr_paren) ops_member (string | int)`. The AST type `ExprMember.member`
is `string | number`, so the parser models `->` as a fixed-key lookup. In PostgreSQL `->` is an ordinary binary
operator on `json`/`jsonb` whose right operand is any `text` or `int` expression (section 9.16.1, table "json and jsonb Operators"), and
keys held in a column or parameter are common. A fix needs either a binary-expression fallback when the right side
is not a literal, or a widened AST type; the second is a breaking change, which may be why it is this way.

## D. Parenthesised join with an alias, or nested on the right (related to #153)

```
SELECT * FROM (a JOIN b ON TRUE) AS d                    Syntax error at line 1 col 34
SELECT * FROM a LEFT JOIN (b JOIN c ON TRUE) ON TRUE     Syntax error at line 1 col 30
```

`src/syntax/select.ne:55`: `lparen select_from_item_joins rparen {% get(1) %}` flattens the parenthesised join
into the outer FROM list, so there is no node to hang an alias on and no way to use it as the right operand of an
outer join. Issue [#153](https://github.com/oguimbal/pgsql-ast-parser/issues/153) (open, 2024) reports the second
form as generated by Sequelize. PostgreSQL 18 SELECT reference, `from_item`: `( join_clause ) [ [ AS ] alias ]`.
Add the alias form as a note on #153 rather than as a new issue.

## Known, not new

| Statement | Upstream |
|---|---|
| `SELECT a FROM t INTERSECT SELECT b FROM u` (also `EXCEPT`) | [#117](https://github.com/oguimbal/pgsql-ast-parser/issues/117), open since 2022; `union.ne` has only `UNION [ALL]` |
| `WITH RECURSIVE a AS (SELECT 1 UNION SELECT 2) SELECT 1` | `with.ne:11-17` requires a column list; fixed in open PR [#174](https://github.com/oguimbal/pgsql-ast-parser/pull/174); see also [#44](https://github.com/oguimbal/pgsql-ast-parser/issues/44) |
| `WITH a AS ((SELECT 1)) SELECT 1`, `((SELECT 1))` | open PR [#146](https://github.com/oguimbal/pgsql-ast-parser/pull/146) (2023) |
| `SELECT a->'x'::int` parses as `(a->'x')::int` | [#168](https://github.com/oguimbal/pgsql-ast-parser/issues/168); PostgreSQL gives `::` higher precedence |
| `SELECT 1_000::int` | PostgreSQL 16 syntax; see the exponent-literal finding |

## Not a bug for this library alone: `a = b = c`

`SELECT a FROM t WHERE a = b = c` is accepted and re-printed as `((a = b) = c)`, because `expr.ne:73` makes `=`
left-recursive. PostgreSQL 18 rejects it (section 4.1.6: comparison operators are non-associative since 9.5;
confirmed on a 14.19 server: `syntax error at or near "="`). sql-parser-cst and sql-formatter accept it too, so
this is shared leniency rather than a report for this package alone.
